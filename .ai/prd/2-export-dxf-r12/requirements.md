# OCSSTACK-2 Add Machine-Compatible Binary DXF R12 Export

## Goal

Add an explicit, non-destructive export path that writes model-space geometry
as a machine-compatible binary DXF R12 (`AC1009`) file without changing the
normal `SAVE` or `SAVEAS` behavior.

## Background

Open CAD Studio v0.9.2 can label output as DXF R14, but minimal files written by
the pinned `acadifc/acadrust` revision are rejected by Fusion 360 and by a
legacy machine importer. Controlled tests proved that the geometry itself is
not the cause. The writer emits version-inappropriate data, including group
`91=0` in every R14 `CLASS` record; removing that field makes an otherwise
working QCAD document import successfully. Additional incompatibilities remain
in a complete OCS document.

The exact pinned library revision exposes binary DXF writing and declares R12
support, but it does not perform a complete R12 down-conversion: it always
writes `CLASSES` and `OBJECTS` and can emit post-R12 entity types such as
`LWPOLYLINE`. A dedicated compatibility exporter is therefore required.

## Requirements

### Functional Requirements

- [ ] FR1: Register `EXPORTDXFR12` as the canonical command and `EXPORTR12` as
  an alias for the same operation.
- [ ] FR2: Export a cloned document snapshot and never mutate the open drawing,
  its dirty state, active layout, undo history, file path, or selected entities.
- [ ] FR3: Export only model-space geometry; omit paper-space layouts,
  viewports, layout dictionaries, and other presentation-only state.
- [ ] FR4: Write binary DXF R12 with header version `AC1009` and the standard
  binary DXF sentinel.
- [ ] FR5: Preserve native R12 manufacturing geometry including `LINE`, `ARC`,
  `CIRCLE`, `POINT`, and compatible 2D `POLYLINE` records.
- [ ] FR6: Convert every `LWPOLYLINE` to legacy
  `POLYLINE/VERTEX/SEQEND`, preserving vertex order, closed state, elevation,
  layer, and bulge values without changing geometry.
- [ ] FR7: Generate minimal version-correct R12 header, tables, blocks, and
  model-space records; do not write `CLASSES`, `OBJECTS`, `BLOCK_RECORD`,
  subclass markers, layout objects, or post-R12 group codes.
- [ ] FR8: Recalculate `$EXTMIN/$EXTMAX` from the exported model geometry and
  produce finite values for non-empty drawings.
- [ ] FR9: Preserve layer names where R12-compatible, map unsupported or missing
  linetypes to `CONTINUOUS`, and report every compatibility substitution.
- [ ] FR10: Refuse export with a clear list of unsupported entity types whenever
  lossless conversion is unavailable; never silently drop geometry.
- [ ] FR11: Support both native and WebAssembly application targets. The web
  target must generate bytes in memory and download a `.dxf` file through the
  existing file-dialog/file-handle abstraction.
- [ ] FR12: After serialization, re-read the generated bytes and verify the
  binary sentinel, `AC1009`, entity counts/types, finite extents, structural
  termination, and absence of forbidden post-R12 sections/codes.
- [ ] FR13: Suggest a default filename ending in `_R12.dxf` without overwriting
  the source drawing unless the user explicitly selects an existing target.
- [ ] FR14: Report success with exported entity counts and compatibility
  conversions, or failure without leaving a partial output file.

### Non-Functional Requirements

- [ ] NFR1: Keep normal `SAVE`, `SAVEAS`, DXF R14+, and DWG behavior unchanged.
- [ ] NFR2: Put generic version-aware serialization fixes in
  `acadifc/acadrust`; keep only command/UI and export-policy logic in Open CAD
  Studio.
- [ ] NFR3: Keep the Open CAD Studio fork delta isolated and suitable for an
  upstream pull request; avoid copying or reimplementing the complete DXF
  writer in the application repository.
- [ ] NFR4: Use generated or anonymized test drawings only. Do not commit
  customer CAD files, private paths, hostnames, addresses, or runtime data.
- [ ] NFR5: Make output deterministic for the same normalized input, excluding
  explicitly documented volatile metadata.
- [ ] NFR6: Bound additional memory to one cloned/normalized document plus the
  output buffer and surface an actionable error on allocation/serialization
  failure.
- [ ] NFR7: Preserve the repository workflow `local -> anonymized GitHub ->
  server`; production activation requires an exact verified revision and a
  stack-local image rebuild.

## Scope

### In Scope

- Canonical command `EXPORTDXFR12` and alias `EXPORTR12`
- Binary R12 model-space compatibility export
- Lossless conversion of 2D lightweight polylines to legacy polylines
- Minimal version-correct document normalization
- Native and web save/download flows
- Unit, integration, round-trip, and regression tests
- Public reusable documentation and upstream contribution preparation
- Container rebuild and exact-revision rollout plan

### Out of Scope

- Changing the default format or behavior of `SAVE`/`SAVEAS`
- DXF R12 DWG output
- Paper-space/layout export
- Silent tessellation of splines, ellipses, hatches, dimensions, 3D solids, or
  unsupported application entities
- Automatic upload to a machine or network share
- LDAP, Nextcloud, reverse-proxy, firewall, or unrelated stack changes
- Committing the diagnostic files from the user's Downloads directory

## Technical Notes

- The deployed dependency is `OpenAEC-Foundation/acadifc` revision
  `6f9a92f665b88c29970b7efd658ecf30dc589750`.
- That revision exposes `DxfWriter::new_binary()` and `DxfVersion::AC1009`, but
  its `SectionWriter` requires additional version-aware behavior for genuine
  R12 output.
- Open CAD Studio currently maps save formats only down to R14 and calls
  `DxfWriter::new()` for DXF output. The new operation must use a separate path.
- Expected OCS integration points are command dispatch and registration,
  application message variants, asynchronous update/file handling, locale
  strings, and a new isolated IO module.
- The compatibility report should be a typed result rather than text parsed
  from logs.

## Acceptance Criteria

- [ ] AC1: Both `EXPORTDXFR12` and `EXPORTR12` invoke the same exporter and are
  present in command autocomplete.
- [ ] AC2: A generated one-line drawing exports as binary `AC1009`, reopens with
  the project reader, and preserves exact endpoints.
- [ ] AC3: A closed `LWPOLYLINE` containing straight and bulged segments exports
  as legacy `POLYLINE/VERTEX/SEQEND` with identical topology and bulges.
- [ ] AC4: Output contains no `CLASSES`, `OBJECTS`, `BLOCK_RECORD`, `LWPOLYLINE`,
  layout viewport, subclass marker, or known post-R12 group code.
- [ ] AC5: `$EXTMIN/$EXTMAX` match the exported geometry within a documented
  floating-point tolerance.
- [ ] AC6: An unsupported entity causes an explicit failure naming the entity
  type and creates no final file.
- [ ] AC7: Native and browser builds compile and complete their respective file
  save/download flows.
- [ ] AC8: Regression fixtures reproduce the discovered R14 `CLASS 91` problem
  without containing private drawings, and the R12 exporter avoids the entire
  incompatible section.
- [ ] AC9: A representative generated machine drawing imports successfully in
  Fusion 360 and on the target machine before rollout approval.
- [ ] AC10: Standard save/export regression tests pass unchanged.
- [ ] AC11: Public tracked files pass privacy review and contain no private
  infrastructure or CAD data.
- [ ] AC12: The deployed container reports the tested revision, remains healthy,
  and can be rolled back to the previous image without touching other stacks.

## Open Questions

- Q1: Should the first release support `TEXT` and legacy `INSERT`, or fail on
  them until representative machine tests exist?
  - Answer: Default to fail-safe rejection; add them only with verified tests.
- Q2: Should unsupported curves be tessellated automatically?
  - Answer: No for the first release; silent geometric approximation is outside
  scope. A later explicit approximation mode may be designed separately.
- Q3: Should the exporter be binary-only?
  - Answer: Yes. The command contract is binary R12; an ASCII diagnostic mode,
  if needed, remains test-only or a future explicit command option.
